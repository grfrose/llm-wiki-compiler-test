# llm_wiki 构建与查询逻辑移植可行性评估报告

**评估日期**: 2026-08-06  
**评估对象**: 将 llm_wiki (Python+Rust+TS) 的构建与查询逻辑移植到 llm-wiki-compiler-test (TypeScript CLI)  
**评估目标**: 解决 llm-wiki-compiler-test 细节丢失问题，提升 wiki 页面信息完整性

---

## 一、执行摘要

### 总体结论

**✅ 完全可行** | **工作量**: 11-20 人天 | **无架构级阻断点**

llm_wiki 的详细信息保留能力源于三个核心设计的组合：**Prompt 设计 + Schema/Purpose 双重指导 + 两阶段 LLM 分析**。这些机制中，80% 是 TypeScript 代码，可直接移植；20% 是 Rust 代码，可用 Node.js 等价库替换。

### 关键发现

1. **技术栈澄清**: llm_wiki 并非"Python+Rust+TS"三语言混合。Python 仅 1 个调试脚本（~200 行），**不参与核心流程**。核心逻辑集中在 TypeScript (~30K LOC) + Rust (~8K LOC)。

2. **根因定位**: llm-wiki-compiler-test 细节丢失的 5 个根因中，**2 个可通过纯 prompt 文本修改解决**（最高投资回报率），1 个需要复制 llm_wiki 的 TS 模块，2 个需要替换技术栈。

3. **移植路径**: 推荐三阶段渐进式移植。Phase 1a（Prompt 改进）仅需 **0.5-1 天**，预期带来 **40-60% 的细节保留提升**。

## 二、llm_wiki 真实技术栈分析

### 2.1 语言分布（澄清误解）

| 语言 | 角色 | 代码量 | 核心文件 | 移植难度 |
|------|------|--------|----------|----------|
| **TypeScript** | 业务流程、Prompt 模板、分块算法、图算法、LLM 调用 | ~30K LOC | `ingest.ts`, `text-chunker.ts`, `wiki-schema.ts`, `wiki-graph.ts` | ✅ **大部分可直接复制** |
| **Rust (Tauri)** | 向量数据库、搜索融合、文件解析、Agent 工具、Embedding fetch | ~8K LOC | `vectorstore.rs`, `search.rs`, `fs.rs`, `agent/` | ⚠️ 需替换为 Node.js 等价库 |
| **Python** | **仅 1 个调试脚本** | ~200 LOC | `scripts/debug_ollama_tokens.py` | ✅ **忽略不计** |

> **重要澄清**: 之前对比文档中描述的"Python+Next.js+Rust/Tauri"有误导性。Python 不参与核心 ingest/query 流程，仅用于调试 Ollama token 计数。

### 2.2 Rust 代码职责边界

| Rust 模块 | 职责 | 代码量 | TS 替代方案 |
|-----------|------|--------|-------------|
| `vectorstore.rs` | LanceDB 向量存储 CRUD | ~1,200 LOC | `@lancedb/lancedb` npm 包（官方维护） |
| `search.rs` | BM25 + 向量 + 图融合，RRF 算法 | ~1,000 LOC | `minisearch` + 自实现 RRF（5 行代码） |
| `fs.rs` | 文件读写、PDF/Office 解析 | ~1,500 LOC | `fs/promises` + `pdf-parse`/`mammoth` |
| `agent/` | Tool calling loop（8 tools, max 8 iterations） | ~3,000 LOC | OpenAI/Anthropic SDK（TS 更成熟） |
| `embedding_fetch` | HTTP 请求 Embedding API | ~200 LOC | Node.js `fetch` |

**结论**: Rust 代码量有限且职责清晰，替换成本可控。

## 四、细节丢失的 5 个根因与移植优先级

### 4.1 根因分析

| 根因 | llm_wiki（好） | llm-wiki-compiler-test（差） | 影响程度 | 移植优先级 | 工作量 |
|------|----------------|------------------------------|----------|-----------|--------|
| **1. Prompt 设计** | "Include ALL relevant information" + schema/purpose 注入 | "3-8 concepts, not trivial details" + "Be concise" | ⭐⭐⭐⭐⭐ | **P0**（最高 ROI） | 0.5 天 |
| **2. Schema/Purpose 机制** | schema.md 路由页面类型 + purpose.md 注入 system prompt 指导 AI | **无等价物**，AI 不知"为什么这样做" | ⭐⭐⭐⭐⭐ | **P0** | 2 天 |
| **3. 两阶段分析** | Phase 1 完整分析（保留所有细节） → Phase 2 生成（基于分析结果） | 提取元数据（3-8 concepts + one-line summary） → 生成（中间丢失语义连接） | ⭐⭐⭐⭐ | P1 | 2 天 |
| **4. 向量存储性能** | LanceDB ANN 索引，支持大规模 chunk 检索 | JSON 文件全内存加载，线性扫描余弦相似度 | ⭐⭐⭐ | P1 | 5 天 |
| **5. 源文件内容截断** | Markdown-aware 分块（保护代码块/表格/heading 边界） | `slice(0, n)` 简单字符截断（可能在句子中间截断） | ⭐⭐⭐ | P1 | 0.5 天（复制 chunker） |

### 4.2 根因详解

#### 根因 1: Prompt 设计（文件: `src/compiler/prompts.ts:130-132, 179, 284`）

**问题代码**:
```typescript
// Line 130: 硬限制概念数量
"and identify 3-8 distinct, meaningful concepts worth documenting as wiki pages."

// Line 132: 指令过滤"琐碎细节"
"Focus on key ideas, techniques, patterns, or entities — not trivial details."

// Line 179, 284: concise 优先于 thorough
"Write in a neutral, informative tone. Be concise but thorough."
```

**影响**: LLM 被指令主动过滤"琐碎细节"，但"琐碎"的定义由 LLM 自主判断，导致用户认为重要的细节（数据点、示例、代码片段）被丢弃。

**llm_wiki 对比**:
```typescript
// llm_wiki ingest.ts:buildGenerationPrompt
"Include ALL relevant information from the source material."
```

#### 根因 2: Schema/Purpose 机制（文件: `llm_wiki/src/lib/wiki-schema.ts`, `templates.ts`）

**问题**: llm-wiki-compiler-test 无 schema.md 和 purpose.md 文件支持，AI 在生成页面时缺乏：
- **页面类型路由规则**（entity/concept/source/comparison 各放在哪个目录）
- **项目级语境**（为什么构建这个 wiki？受众是谁？关键问题是什么？）

**影响**: 生成的页面类型单一，仅 `concepts/` 目录；页面内容缺乏针对性（不知"为什么这样做"）。

**llm_wiki 对比**: schema.md 定义 5 种页面类型 → 5 个目录，purpose.md 注入 system prompt 指导 AI 理解项目目标。

#### 根因 3: 两阶段分析（文件: `src/compiler/extraction-phase.ts:187`）

**问题**: Phase 1 提取阶段的输出是 **3-8 个 concept 的 JSON 数组**（`name`, `summary`），而非完整分析文本。

```typescript
// llm-wiki-compiler-test extraction-phase.ts:187
const extraction = await extractionLLM.complete({
  prompt: buildExtractionPrompt(sources),
  schema: z.object({
    concepts: z.array(z.object({
      name: z.string(),
      summary: z.string()  // "One-line description"
    }))
  })
})
```

**影响**: 中间环节的语义信息（概念间的联系、矛盾、技术权衡）被压缩为一行摘要，Phase 2 生成时缺少足够上下文。

**llm_wiki 对比**: Phase 1 输出是**完整分析文本**（4096 tokens），保留所有细节；Phase 2 基于分析文本生成页面，信息已在分析中结构化。

#### 根因 4: 向量存储性能（文件: `src/utils/embeddings-store.ts:307`）

**问题**: 使用 JSON 文件存储所有 embedding 向量，查询时需要：
1. 加载整个 JSON 文件到内存（~MB 级）
2. 线性扫描所有向量计算余弦相似度
3. 无 ANN 索引，O(N) 复杂度

**影响**: 当 wiki 页面数量 >500 时，查询延迟显著增加（>2 秒），chunk 级检索（需要 top-K 个 chunk）性能更差。

**llm_wiki 对比**: LanceDB 提供 ANN 索引（IVF/PQ），查询延迟 <100ms（10K 页面对比）。

#### 根因 5: 源文件内容截断（文件: `src/compiler/prompt-budget.ts:68-75`）

**问题**: 超预算时使用简单字符截断：

```typescript
// llm-wiki-compiler-test prompt-budget.ts:68-75
if (totalChars > budget) {
  const perSource = Math.floor(budget / slices.length);
  slices.forEach((s) => {
    if (s.content.length > perSource) {
      s.content = s.content.slice(0, perSource) + "\n\n[Content truncated]";
    }
  });
}
```

**影响**: 截断不考虑 Markdown 语义边界，可能在句子中间、代码块内部、表格中间截断，导致：
- 语义不完整（句子断裂）
- 代码块损坏（``` 未闭合）
- 表格格式破坏（| 未对齐）

**llm_wiki 对比**: `text-chunker.ts` 使用 Markdown-aware 分块（保护代码块/表格，按 heading 边界切割），保证语义完整性。

## 五、三阶段渐进式移植方案

### Phase 1a: Prompt 层改进（**0.5-1 天，最高投资回报率**）

**目标**: 仅改动 prompt 文本和 schema/purpose 支持，不改架构，观察效果改善

**改动范围**:
- `src/compiler/prompts.ts`（4 处 prompt 文本）
- 新增 `schema.md` / `purpose.md` 文件加载逻辑
- 在 Phase 1/2 prompt 注入 schema/purpose 上下文

**预期效果**: 细节保留提升 40-60%（数据点、示例、代码片段保留率）

**验证方式**: 选 3 份已知细节丰富的源文件，对比改进前后 wiki 页面字符数和关键数据点保留率

---

### Phase 1b: 架构层改进（**5-7 天**）

**目标**: 复制 llm_wiki 的核心 TS 模块，替换 llm-wiki-compiler-test 的简化实现

**改动范围**:
- 复制 `text-chunker.ts` → 替换 `embeddings-chunks.ts`
- 复制 `buildAnalysisPrompt` + `buildGenerationPrompt` → 替换 `prompts.ts`
- 复制 schema/purpose 解析 → `wiki-schema.ts`, `templates.ts`
- 引入 `analyzeLongSourceInChunks` → 替换 `slice(0, n)` 截断
- 替换 graph 实现为 graphology

**预期效果**: 细节保留提升 70-80%（接近 llm_wiki 水平）

**验证方式**: 对比改进前后 wiki 页面与 llm_wiki 生成的页面（同源文件），字符数差异 <20%

---

### Phase 2: 查询层升级（**4-6 天**）

**目标**: 升级检索质量和容量，匹配 llm_wiki 的查询能力

**改动范围**:
- 引入 `@lancedb/lancedb` → 替换 JSON embeddings 存储
- 引入 `minisearch` → 升级 BM25（保留 CJK 支持）
- 实现 RRF 融合（5 行代码）→ 替换加权求和
- 升级 graph：graphology → 替换当前 BTreeMap 图
- 默认开启图扩展（depth=1，配额 15-30%）

**预期效果**: 查询召回率提升 30-50%，查询延迟降低 80%（10K 页面对比）

**验证方式**: 构建 1000 页面测试集，对比查询召回率和平均延迟

---

### Phase 3: Agent 模式（**3-5 天，可选**）

**目标**: 引入查询时多工具协作，支持复杂查询

**改动范围**:
- 实现 tool calling loop（OpenAI/Anthropic SDK）
- 注册 4 个核心 tool：`wiki.search`, `wiki.read_page`, `graph.search`, `source.search`
- 最大 8 次迭代，带取消机制
- 实现权限策略（禁用 `shell.exec` 或白名单）

**预期效果**: 支持复杂查询（"对比 A 和 B 的架构差异"），查询准确率提升 20%

**验证方式**: 10 个复杂查询测试用例，对比 Agent 模式 vs 单轮查询的准确率

## 六、风险矩阵
